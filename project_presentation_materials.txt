1. Короткое описание проекта

HBS Social: Course Allocation with Friendships - это детерминированный механизм распределения студентов по курсам на основе HBS-style snake draft, расширенный социальными предпочтениями. В классической постановке студент получает набор мест на курсах с учетом ограниченных вместимостей курсов. В этом проекте добавлено то, что студенту может быть важно не только попасть на конкретный курс, но и попасть туда вместе с друзьями.

Главная идея: индивидуальная полезность курса и социальная полезность от совпадения с друзьями объединяются в одну функцию полезности. Затем алгоритм сначала строит начальное распределение через snake draft, а потом может улучшать его локальным поиском: swap, drop-add или hybrid, с глобальной или персональной целью.

Проект написан на Python 3.10+ и использует только стандартную библиотеку. Есть CLI, локальный web UI, генератор синтетических данных, экспериментальный pipeline, интерактивная HTML-визуализация и набор тестов.


2. Академическая постановка задачи

Course allocation можно формулировать как one-sided combinatorial assignment problem: студенты получают допустимые наборы неделимых мест на курсах при ограничениях вместимости курсов и без реальных денежных трансферов.

Классический пробел: многие механизмы распределения курсов предполагают, что предпочтения студентов независимы. В реальности студент может предпочитать курс не только из-за содержания, преподавателя или расписания, но и потому, что там будут друзья.

Вклад проекта:
- Расширяет HBS-style course allocation механизм directed friendship preferences.
- Добавляет course-specific социальный слой: студент A может хотеть быть на курсе C вместе со студентом B.
- Использует student-specific параметр `LambdaFriend`, который задает баланс между индивидуальной и социальной полезностью.
- Делает социальную полезность reactive: бонус считается только от друзей, которые уже распределены на данный курс.
- После начального draft запускает local-search улучшения.
- Оценивает результат не только по total utility, но и по fairness, inequality, ranks и friend overlaps.

Возможный тезис для выступления:
Стандартное распределение курсов теряет важный социальный фактор, потому что считает предпочтения студентов независимыми. Этот проект показывает, как добавить направленные friendship preferences в HBS-style draft так, чтобы механизм оставался детерминированным, измеримым и экспериментально улучшаемым после первичного распределения.


3. Что означает HBS-style snake draft в проекте

Алгоритм строит случайный, но воспроизводимый порядок студентов через seed. Затем проходит несколько раундов:
- нечетные раунды идут в прямом порядке;
- четные раунды идут в обратном порядке.

Пример:
Если seeded permutation = [S2, S1, S3], то:
- round 1: S2, S1, S3;
- round 2: S3, S1, S2;
- round 3: S2, S1, S3.

На каждом ходе студент выбирает лучший доступный курс из feasible set:
- у курса есть свободная capacity;
- студент еще не получил этот курс;
- студент не превышает лимит `b` курсов.


4. Входные данные

Проект использует две обязательные CSV-таблицы и одну опциональную.

Table 1: individual course preferences
Колонки:
- StudentID: идентификатор студента.
- CourseID: идентификатор курса.
- Score: raw score, используется для tie-breaking.
- Position: ранк курса для студента, 1 = самый предпочтительный.

Смысл: насколько студент хочет конкретный курс.

Table 2: directed friend preferences
Колонки:
- StudentID_A: студент, выражающий предпочтение.
- StudentID_B: друг.
- CourseID: курс, в контексте которого задана дружеская связь.
- Position: ранк друга для данного курса.
- Score: интенсивность предпочтения, может отсутствовать.

Смысл: "Student A хочет быть на CourseID вместе со Student B".

Важная особенность: предпочтения направленные. Если A хочет быть с B, это не означает, что B обязательно хочет быть с A.

Table 3: per-student social weight
Колонки:
- StudentID.
- LambdaFriend.

`LambdaFriend` лежит в [0, 1]:
- lambda = 0: студенту важны только индивидуальные course preferences.
- lambda = 1: студенту важна только friendship/social component.
- если Table 3 не передана, используется default lambda = 0.5.


5. Функция полезности

Итоговая полезность курса для студента:

U(s, c) = (1 - lambda_s) * Base(s, c) + lambda_s * FriendBonusNorm(s, c)

где:
- Base(s, c) - индивидуальная полезность курса из Table 1.
- FriendBonusNorm(s, c) - нормализованный социальный бонус от друзей.
- lambda_s - социальный вес конкретного студента.

Base utility:
Позиция курса переводится в число [0, 1]:

Base(s, c) = (K - position) / (K - 1), если K > 1.

Пример для K = 4:
- position 1 -> 1.0;
- position 2 -> 0.6667;
- position 3 -> 0.3333;
- position 4 -> 0.0.

Friend preference:
Если в Table 2 есть Score, он нормализуется min-max scaling в [0, 1].
Если Score отсутствует, используется fallback по позиции друга:

FriendPreference = (K_friends + 1 - position) / K_friends

Это дает:
- rank 1 -> 1.0;
- последний rank -> 1 / K_friends.

Reactive friend bonus:
Друг учитывается только если он уже распределен на тот курс, который сейчас рассматривает студент.

FriendBonus(s, c) = сумма весов Pref(s, friend, c) для тех друзей, у которых course c уже есть в allocation.

Зачем reactive:
- Убирает circular dependency.
- Делает выбор последовательным и совместимым с draft.
- Позволяет объяснить каждый ход через текущую историю распределения.


6. Правило выбора курса и tie-breaking

Для каждого хода алгоритм считает U(s, c) для всех feasible courses и выбирает максимум. Если полезности почти равны, используется deterministic tie-breaking:

1. максимальная utility, с округлением/толерансом около 1e-9;
2. максимальный Score из Table 1;
3. минимальная Position из Table 1;
4. seeded random value;
5. стабильный CourseID.

Это важно для reproducibility: один и тот же seed дает тот же allocation и те же summary metrics.


7. Post-allocation improvement

После начального draft можно запустить `post_iters` итераций улучшения. В проекте есть 3 типа moves и 2 типа objectives, всего 6 режимов:

Move types:
- swap;
- drop-add;
- hybrid.

Objective scopes:
- global;
- personal.

Canonical modes:
- swap-global;
- swap-personal;
- drop-add-global;
- drop-add-personal;
- hybrid-global;
- hybrid-personal.

Swap:
Алгоритм ищет обмен курсами между двумя студентами:
(s1, c1) <-> (s2, c2)

Global version принимает swap только если растет глобальная welfare:
Delta W_global > 0.

Personal version принимает oriented swap, если растет utility текущего студента:
Delta U_student > 0.

Drop-add:
Для студента строится желаемый top-b набор из:
- текущих курсов;
- курсов со свободной capacity.

Затем алгоритм проверяет, стоит ли заменить текущий набор на новый.

Hybrid:
Комбинирует add/drop и swap:
- если target course имеет свободное место, пробует 1-for-1 replacement;
- если target course заполнен, пробует swap с holder этого курса;
- порядок прохода повторяет snake-order.

Global objective:
Оптимизирует сумму полезностей всех студентов.

Personal objective:
Оптимизирует локальный выигрыш текущего студента, даже если глобальный эффект может быть хуже.

  --csv-a tables/table1_individual.csv \
  --csv-b tables/table2_pair.csv \
  --csv-lambda tables/table3_lambda.csv \
  --cap-default 80 --b 3 --seed 11

python3 hbs_social.py \
  --csv-a tables/table1_individual.csv \
  --csv-b tables/table2_pair.csv \

  --draft-rounds 3 \
  --post-iters 10 \

  --objective-scope global \
  --seed 11 \
  --progress

python3 tests/run_all_tests.py

14. Synthetic data generator

File:
- `generate/generate_tables.py`.

It creates:
- Table 1: individual preferences.
- Table 2: top-K friend preferences per student/course.
- Table 3: LambdaFriend values.

Generator properties:
- deterministic if seed is set;
- students are named S1, S2, ...;
- courses are named C1, C2, ...;
- scores are sampled from a soft distribution, with more probability around the middle;
- positions are derived by sorting scores with small random tie noise;
- optional adjacent swaps can add ranking noise;
- Table 2 disallows self-pairs;
- Table 2 validates unique friends and contiguous positions inside each student/course group;
- Table 3 can assign the same lambda to every student.

Current table files found in `tables/`:
- `table1_200x8.csv`: 200 students x 8 courses, 1600 data rows.
- `table2_200x8.csv`: 200 students x 8 courses x top-3 friends, 4800 data rows.
- `table1_200x10.csv`: 200 students x 10 courses, 2000 data rows.
- `table2_200x10.csv`: 200 students x 10 courses x top-3 friends, 6000 data rows.
- `table1_200x12.csv`: 200 students x 12 courses, 2400 data rows.
- `table2_200x12.csv`: 200 students x 12 courses x top-3 friends, 7200 data rows.
- lambda files include constant values from 0.0 to 1.0 and random variants.

20. Limitations and caveats

This is a research/prototype allocation engine, not a production university registration system.

The current datasets are synthetic, generated by `generate_tables.py`. Real student data would require privacy handling, stronger validation and ethical review.

The model includes friendship preferences but does not include every real scheduling constraint unless extended: for example timetable conflicts, prerequisites, professor preferences, section times or waitlists.

The saved experiment evidence should be presented as preliminary computational evidence from local artifacts, not as a final theoretical result.

The social objective can create trade-offs:
- more friend overlap;
- higher total welfare;
- worse average rank;
- lower share of top-3 assigned courses;
- slightly higher inequality in saved hybrid-global evidence.

The current abstract/review notes say that if the paper does not formally define "reactive social utility", use safer wording such as "friendship-based social term" or "social utility term".


21. Suggested 15-minute narrative, not a slide deck

Opening, about 1 minute:
Explain that course allocation usually treats students as independent, but in practice students often care who they take a course with.

Problem and gap, about 2 minutes:
Define one-sided combinatorial assignment with indivisible course seats and capacity constraints. State that standard mechanisms do not model friendship relations.

Model, about 3 minutes:
Introduce Table 1, Table 2 and Table 3. Explain Base utility, directed friend preferences and lambda. Emphasize that friendship preferences are directed and course-specific.

Mechanism, about 3 minutes:
Explain seeded snake draft, reactive friend bonus and deterministic tie-breaking. Show why reactive bonus avoids circular dependency.

Post-allocation improvement, about 2 minutes:
Explain that draft creates a feasible initial point, then local search can improve it. Present the 3 x 2 matrix: swap/drop-add/hybrid crossed with global/personal.

Experiments and metrics, about 3 minutes:

23. Prompt-ready project summary

Use this paragraph as a compact input to a presentation-generating AI:

Create a 15-minute academic presentation about "HBS Social: Course Allocation with Friendships", a Python research prototype for deterministic HBS-style snake draft course allocation with directed friendship preferences. The project models course allocation as a one-sided combinatorial assignment problem with indivisible course seats and capacity constraints. It extends classic individual course preferences with a course-specific directed friendship term. Each student's utility is U(s,c) = (1 - lambda_s) * Base(s,c) + lambda_s * FriendBonusNorm(s,c), where lambda_s controls the individual/social trade-off. The friend bonus is reactive: a friend contributes only if already allocated to the candidate course, avoiding circular dependency. The initial allocation uses seeded snake draft and deterministic tie-breaking by utility, score, position, seeded random and CourseID. After the draft, the system can run post-allocation local search with six modes: swap-global, swap-personal, drop-add-global, drop-add-personal, hybrid-global and hybrid-personal. The framework exports allocation logs, post-phase logs, summary metrics and extended fairness metrics, including total utility, Gini, Jain, Theil, Atkinson, percentiles, rank satisfaction and friend overlap. It includes CLI, local web UI, mode comparison, experiment sweeps, SQLite persistence, interactive visualization and tests. In saved A_200x8 partial experiments with 200 students, 8 courses, capacity 80, b=3, seeds 11-20, hybrid-global improved mean total utility from 371.310 to 384.805 by post_iters=5, about +3.63%, and increased average friend overlaps from 3.7145 to 4.6965, about +26.44%. The trade-off is that average assigned position worsened from 2.186 to 2.434, share_top3 fell from 0.872 to 0.796, and gini_total_norm rose from 0.05238 to 0.05576. Emphasize the contribution, mechanism, utility model, post-allocation improvement matrix, reproducibility and welfare/fairness/social-satisfaction trade-off.
